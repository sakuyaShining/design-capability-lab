# 局部小样的逐批评价

2026-11-11。以下是实际浏览器检查和 Agent 设计评判，不是人类可用性研究。数据为同一份合成样例；不以不同皮肤计作不同版本。

## 第一批：A 分栏 / B 关系图

已实现、运行并查看桌面／手机截图。证据在 [round01](../../runs/prototypes-round01/verification.json)。

- **A**：任务扫描和详情就近，直接原因容易逐项读；但全量任务清单与当前前置重复，长列表拉长页面，手机的列表区和详情区需要额外定位。适合日常工作入口，暂不作为复杂依赖总览。
- **B**：共享前置与分支结构在空间中可见，比列表更容易讨论关系；但详情退到图下方，图中标题空间有限，手机转列表后缺少清楚的关系连线。适合辅助总览，暂不作为手机主交互。
- **检查发现并修正**：A 的全量任务选择最初与前置追踪共用动作，会把无关任务错误加入“需要”路径；已改为切换原任务。B 的任务选择器最初未使用范围筛选；已修正。筛选不会隐藏当前路径中的跨项目依赖。
- **下一批要解决**：用 C 保留已走过的各层，用 D 将视觉与内容重点转向“具体原因与下一步”，压缩大标题区域。不是继续给 A/B 换配色。

两种均通过原任务→前置→人工阻塞原因→返回原任务、保留项目筛选与查询、缺失引用提示、390px 无页面横向溢出、减少动态效果和无脚本错误检查。通过这些检查不证明哪种更易用。

## 第二批：C 逐层栏 / D 阻塞档案

依据第一批结果制作，实际运行并查看截图。证据在 [round02](../../runs/prototypes-round02/verification.json)。

- **C**：保留每层的前置列表与选择，适合追溯一条链。多个并行分支仍需回到前一栏比较；路径过深会增加桌面横向空间，手机堆叠后较长。作为深层排查的候选，需限制可见层数或折叠已离开的层。
- **D**：原因、对象、状态与预期产出在同一叙事内，能明确“待开始但前置未满足”和“人工标记阻塞”的差别。更接近工作判断，但不擅长展示多个任务共享同一前置，长内容在手机上显著增高。适合任务详情的解释区。
- **下一批要解决**：E 尝试一次只突出一个排查问题，降低首屏负担；F 用矩阵检验多个并行原因与共享前置能否完整比较，避免仅用一条线性路径误导。

两种均通过相同的导航、返回、缺失引用和移动布局检查。截图显示手机可操作，但纵向很长，故不能把“无溢出”直接写成手机体验良好。

## 第三批：E 排查队列 / F 依赖矩阵

依据第二批对首屏负担及并行关系的发现制作。证据在 [round03](../../runs/prototypes-round03/verification.json)。

- **E**：一次突出一个排查问题，较少同时竞争的视觉焦点；保留待查原因清单和原任务。代价是线性推进可能掩盖并行关系；列表顺序只是样例顺序，界面明确不等于优先级，也不把查看过当作已解决。适合不熟悉依赖的引导入口，暂不取代日常工作界面。
- **F**：共享前置、多行影响范围可在同一交叉关系中核查，适合核对关系完整性。代价是密度高、标题空间有限，手机需要表格内部横向滚动。保留为辅助审计视图，淘汰作为默认手机入口的方案。
- **调整**：E 的手机文案不再依赖“右侧”方位；E/F 手机收缩大标题，把空间让给当前对象。六种统一修正了返回后的内容焦点及原任务滚动位置保留。

## 六种方案是否足够不同

| 方案 | 信息分组 | 关系表达 | 主操作路径 | 上下文保存／代价 |
| --- | --- | --- | --- | --- |
| A 分栏 | 任务清单＋详情 | 详情中的直接前置 | 扫描对象→就地阅读 | 清单常驻；内容重复 |
| B 关系图 | 当前对象与两层邻域 | 有方向连线，共享节点一次 | 空间节点→详情 | 图随焦点重构＋路径；手机表达较弱 |
| C 逐层栏 | 每层一个列表 | 相邻栏与已选对象 | 逐栏下钻 | 各层保留；需要较多空间 |
| D 阻塞档案 | 原因、行动、判断依据 | 原因行指向前置对象 | 先读具体原因→追踪 | 叙事焦点＋原任务；共享关系不直观 |
| E 排查队列 | 当前问题＋待查原因 | 一次一个问题，其他并列待查 | 聚焦问题→选下一原因 | 引导与路径；容易误读为顺序优先级 |
| F 依赖矩阵 | 任务行×前置列 | 单元格显式关系 | 交叉核查→点格看对象 | 并行可比；密度和手机滚动代价 |

任意相邻批次在分组、关系和主操作上均改变，不以配色区分版本。A/D 同为文本导向，但清单的对象扫描与原因档案的因果解释是不同入口。C/E 同有引导，但 C 保留每层，E 只突出当前排查问题；不能合并为换皮版本。

## 当前取舍

Agent 建议下一步以 **A 的日常入口＋D 的原因解释** 为候选主方向；C 用于深层追踪，B/F 作为可选关系核查视图，E 留作新手排查实验。尚未制作这一组合，也没有据此决定全站 UI。优先解决手机长页面、深层路径收敛以及共享前置的完整表达，再用真实任务和人类反馈判断是否采用。

研究依据与代价链见[综合报告 P01—P07](../../docs/research-synthesis.md)。返回恢复、焦点和具体动效是原创设计要求，原游戏没有对应连续证据时保留未知。

## 最终验证与限制

[最终主流程](../../runs/prototypes-final/verification.json) 六种均通过：两项未完成前置正确；原任务→方向→人工阻塞原因→返回保持范围与查询；缺失引用可见；390px 页面无横向溢出；减少动态效果时无入场动画；没有脚本运行错误。

[补充检查](../../runs/prototypes-final/responsive-keyboard.json) 覆盖六种×四档屏宽×深浅主题，共 48 组页面溢出检查；键盘 Enter 能进入详情、切换主题和回到原任务，进入详情后焦点落到内容标题；空查询结果不会隐藏正在追踪的依赖。此前各批证据保留，不用最终截图冒充原批状态。

人工已查看六种桌面截图及手机样本；无真人完成率、操作时长或偏好分数。移动检查不等于完整可用性验收，没有屏幕阅读器、大规模数据、循环依赖和真实事务测试。字体许可保留。总控台数据模型、API 和线上站点未修改。
