## 关键取舍

1. **纸面作为主对象。** 旧工作台把标题、状态和操作分置在多个面板；这里把当前任务合成一张纸，状态仪器是外部工具。代价是纸面内容较长，900px 高度下「产出与证据」在首屏下缘。
2. **阶梯只描述一条路径。** 承诺→待开始→进行中→已完成，阻塞与冲突作为叠加标记。没有画分支图，因为真实分支来自依赖，而依赖放在纸面与影响列表里。代价是重开、撤销等反向动作不在阶梯上，只在主操作与记录中出现。
3. **提交前先看影响。** 「提交后」不是固定说明，而是用与提交相同的 model 算出可推进集合的差；提交单再确认一次。代价是每次渲染都做一次模拟，当前 9 条任务无性能问题，规模变大需要缓存。
4. **承诺层级独立。** 想法先停在 00，承诺后才进入执行。这是产品原则「想法不自动变成承诺」的直接表达，也让「暂定方向」不会被误读成待办。
5. **五个项目色只做小面积。** 项目色只出现在签条左边 2px、项目区进度线与编号；主色仍是酸黄。避免五色竞争，也避免一个颜色承担全部状态语义。

## 已知弱点

- **队列头部偏密。** 282px 宽的队列列里同时放标题、本周/全部、计数和四个状态筛选，1440px 下刚好，1280px 以下会更紧。可考虑把范围切换移到项目带。
- **平板上的操作坞与仪器重复。** 1080px 以下出现底部操作坞，和纸面下方的完整仪器同时存在；它保证主操作可见，但重复了一份。是否只在 760px 以下出现，需要真机判断。
- **阶梯与进入条件重复。** 仪器回答「现在能不能、做完会怎样」，纸面回答「具体哪一项、点进去看」。重复是有意的，但两处文案还没有完全分工。
- **数据规模小。** 9 条任务、5 个项目足以验证路径，不能证明长列表、跨项目大量依赖和真实日期压力下的表现。
- **完成记录冲突没有可点样例。** 代码支持冲突判定，样张数据没有制造冲突场景，只有默认数据与四条契约轨迹覆盖正常路径。
- **未做真人评审、屏幕阅读器与真机触控。** 仅做了键盘开合、焦点返回、360px 无横向溢出、减少动态效果与颜色对比度的设计检查。

## 规则对照

规则编号与版本来自 [界面能力规范 0.3](../../../standards/interface-capability/rules.json)。

| 规则 | 本稿用法 |
| --- | --- |
| R01 表面表达职责 | 场地、项目带、队列签、纸面、仪器五种表面各有材质与层级；切角只给可操作项。 |
| R02 首屏焦点与等权条目 | 当前任务标题与纸面最大；项目带与队列是次级；仪器固定可见。 |
| R04 返回与筛选保留语境 | 前置下钻保留路径与滚动；返回恢复来源焦点；筛选不改变当前任务。 |
| R05 状态和焦点分开 | 执行阶段、承诺层级、人工阻塞、完成记录冲突分别表达；查看位置不在任务数据里。 |
| R06 预览与确认边界 | 提交单列出状态变更、条件与影响；取消回到触发控件；校验失败留在表单。 |
| R08 反例约束复用 | 等待、阻塞、想法、完成四种状态都有独立截图与检查；360px 与 1024px 单独检查。 |
| R09 可达性与复盘 | 键盘路径、焦点可见、减少动态效果、44px 触控目标（移动端）；未测屏幕阅读器。 |

## 下一步

2. 用真实任务替换合成快照，验证长标题、真实日期与更多项目时队列和纸面的表现。
3. 若进入产品实现，需要把承诺层级、完成记录、阻塞原因与解除依据写入数据模型，并接入 revision 并发保护与审计。
4. 把「工作」入口之外的项目、资料、记录按同一空间语言展开；本稿不假装它们已经完成。
