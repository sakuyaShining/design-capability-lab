# 工作台流程与状态转移复盘

2026-11-15 · 当前离线工作台 · Agent 评审，待设计审阅。评审对象是 8 条合成任务及其浏览、开始、完成、阻塞和重开流程。采用 DCL Design 0.2.0 的评审方法，用默认流程和异常样例核对动作、守卫、影响和回执。 [可运行原型](index.html) · [当前数据结构和状态图](state-guide.md) · [评审方法](../../../.agents/skills/dcl-design/references/review.md)

当前模型把**任务的执行阶段、依赖及人工阻塞、用户的查看位置**分开，这个划分应保留。比如 T-14 的前置被重开后，它仍处于进行中，只失去记录完成的资格。从 T-15 查看跨项目的 T-14 也会保留原筛选及返回位置。问题集中在完成标记的可信度、受阻后的实际行动，以及变更对其他任务的影响能否被看见。 [共享状态模型](../state-study/model.js) · [原有浏览器记录](../../../runs/project-workbench/state-clarity/verification.json)

## P1 · 会放行错误状态或丢失已记录结果

### 1. 上游完成标记与前置冲突，下游仍然可以开始并完成

打开 [前置全部满足样例](index.html?scenario=clear)。T-15 显示「可以开始」，其直接前置为零项待满足。点开 T-12，它同时显示「已完成」和两项待满足，T-14 也显示「已完成」和一项待满足。回到 T-15，确认开始，再提交完成，两个操作均成功。该样例通过改写阶段造出了矛盾数据。模型递归检查依赖有无缺失和循环，但判断条件是否满足时，仅查看直接前置的完成标记。原有浏览器检查验证了该样例能开始，遗漏了前置自身的有效性。默认样例的正常操作路径没有复现这类矛盾。 [矛盾状态截图](../../../runs/project-workbench/workflow-review/completed-with-pending.png) · [样例种子](app.js#L13) · [推进守卫](../state-study/model.js#L20) · [原有检查](../../../scripts/check-project-workbench.mjs)

应先修正样例，并把「任务已完成时，其所有必需前置也应已完成」作为共享写入和旧数据载入的完整性检查。遇到矛盾记录时，在下游标明具体冲突任务，暂停使用该完成标记放行。验收用一组相同的任务分开测两种数据，一组所有上游真完成，应允许开始；另一组保持 T-12 完成、T-10 待开始，应报告冲突并拒绝推进。

### 2. 重开任务会清空已填结果，解除阻塞也丢掉原记录

默认样例里完成 T-10，确认实际结果可见；随后重开 T-10，完成说明在同一个页面立即消失，预览没有说明这项后果。解除 T-11 的人工阻塞后，原阻塞原因也从当前记录消失。两项都可在刷新前复现。若回到原阶段只是为了复核新要求，此前产物与决定仍有追溯价值。 [重开预览](../../../runs/project-workbench/workflow-review/reopen-preview.png) · [完成、解除及重开写入](../state-study/model.js#L78)

把当前采用的完成结果与历史结果分开。重开时撤销当前完成资格，保留旧结果与重开原因；解除时关闭阻塞记录，保留原原因及解除依据。最小验收是在一轮「完成 → 重开 → 再完成」之后，两次结果仍可区分和查看。产品 v0.2 提案已经覆盖审计及保留历史，现有样张可以先验证操作是否看得懂。 [产品状态提案](../state-study/state-model.md#提交与撤销)

## P2 · 流程可执行，实际工作仍可能卡住

### 3. 等待关系只能表达一种约束

每条 `deps` 既挡开始，也挡完成。默认 T-14 已经进行中，T-10 未完成时，它可以查看前置或再登记一个人工阻塞，任务本身无处记录已核验的模块、待确认项或草稿。这会在重开前置时再次出现。另一个待确认的业务问题是，T-15 是否可以先写方案草稿，等复用验证结束再定稿。这取决于本项目真实约束。 [T-14 样例数据](../prototypes/data.js#L7) · [动作守卫](../state-study/model.js#L56)

先确定哪些依赖限制开始，哪些只限制完成，再决定是否需要给关系加类型。当前就能界定一条可测规则，进行中遇到前置变化时，仍能记录进展，记录完成继续受守卫约束。 [产品 v0.2 的草稿处理](../state-study/state-model.md#状态条件和不变量)

### 4. 面板告诉用户在等谁，遇到多级依赖时给不出当前动作

从默认 T-15 出发，它显示等待 T-12、T-14，只提供「核对待办条件」并跳到前置区。沿任一分支才发现同一个可执行任务 T-10。全局「可推进」能找到 T-10，但面板没有说明它同时挡住两条路径。另一类情况是 T-11，页面写「等待校内负责人的确认」，主动作却是「解除阻塞」，表单只要求补选阻塞前的阶段。用户可以在没有记录外部确认的情况下解除阻塞，工作台无法区别真正解除与手工改标记。 [下一步及其入口](app.js#L60) · [解除表单](app.js#L250) · [操作记录](../../../runs/project-workbench/workflow-review/observations.json)

按当前任务追到可执行的上游，把重复节点合并，说明每项为何与当前任务相关。只有一项明确可做时提供直达，有多项时保留选择。对于人工阻塞，区分尚需发生的事与确认已发生；只在有真实记录时展示负责人或跟进日期。

### 5. 影响提示停在描述，失败与恢复缺少通路

完成 T-10 时，回执写「T-14 现在可推进」，无法从回执点开。重开 T-10 后，T-14 保留进行中，却失去记录完成的资格，回执没有写出这一变化。另一个反例是在 [重开受限样例](index.html?scenario=downstream) 打开 T-12，再把队列筛为 SoC。提示要求核对已完成的 T-15，唯一入口是「任务队列」，而 T-15 已被筛掉。保护下游已完成记录的条件合理，当前界面缺少从拒绝理由进入对应任务的路径。 [重开受限截图](../../../runs/project-workbench/workflow-review/reopen-refusal.png) · [回执计算](app.js#L272)

预览列出真正改变资格的任务，例如「T-14 保持进行中，暂不能记录完成」。回执同时交代新增和失去的资格，让受影响任务能直接打开，并沿用现有的筛选保留及返回。重开遭拒时，把拒绝理由里的任务做成查看入口；如果下游已有结果，由使用者评估重开影响，现有拒绝规则可以先保留。

### 6. 任务的预期产出参与说明，未参与完成判断

T-15 要求一页方案，完成表单提交一个「。」也能使它变成已完成。模型只检验文字长度。当前的「已完成」表达了提交人确认，但单凭这个状态无法判断一页方案是否存在，或是否经过验收。 [完成守卫](../state-study/model.js#L76) · [T-15 预期产出](../prototypes/data.js#L8) · [实测结果](../../../runs/project-workbench/workflow-review/observations.json)

先定义每类样例的最低完成依据。T-15 可要求方案位置或正文，轻量核对任务可以接受简短的核对结论。若确实需要他人验收，再表达审阅结果及其是否影响下游资格。
